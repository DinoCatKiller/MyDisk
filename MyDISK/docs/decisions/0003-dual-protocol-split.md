# ADR-0003：双协议面分离 —— oRPC 控制面 + 原生 HTTP 数据面

|        |                                                          |
| ------ | -------------------------------------------------------- |
| ID     | `D3`                                                     |
| 类型   | 决策（**只增不改**）                                     |
| 状态   | 已接受                                                   |
| 更新   | 2026-10-15                                               |
| 何时读 | 改动上传 / 下载 / 预览取流接口，或想把二进制塞进 oRPC 时 |
| 规模   | ~0.6k token                                              |

## 背景

系统既要端到端类型安全的控制接口（`D1`/`A3`），又要传大体积二进制（8MB 分片、流式下载、预览取流）。oRPC 是 JSON-RPC 语义，处理二进制有固有代价。

## 备选方案

| 方案      | 说明                                                                                 | 优点                                         | 缺点                                                |
| --------- | ------------------------------------------------------------------------------------ | -------------------------------------------- | --------------------------------------------------- |
| A（选中） | 控制面全走 oRPC `/rpc`；数据面走 Hono 原生路由 `/api/upload/*`、`/api/raw/*`、`/dav` | 控制面享受类型安全；数据面直接读写流、无膨胀 | OpenAPI 无法自动覆盖数据面，需手写 spec 片段        |
| B         | 全部走 oRPC（含二进制）                                                              | 单一入口、文档自动                           | base64 膨胀 33%、内存翻倍、无法流式，8MB 分片性能差 |
| C         | 全部走原生 REST + 手写类型                                                           | 无膨胀                                       | 丢失端到端类型安全，前端样板代码爆炸                |

## 决定

**采用 A：控制面（init/complete/abort/列目录/分享/设置…）全部走 oRPC；数据面（分片上传、流式下载、预览取流）走 Hono 原生路由，带签名令牌鉴权，直接读写流。**

**最关键的理由：oRPC 传 8MB 分片要 base64 膨胀 33% 且内存翻倍 —— 二进制必须绕开 JSON-RPC。**

刻意收窄：二进制接口**不放进 oRPC**（返回流 / 二进制的过程一律不进）；数据面接口**不追求自动文档**，改用手写 spec 片段合并（`A3` §11）。

## 影响

- 正面：上传吞吐与内存表现正常；控制面类型安全不受损。
- 代价 / 后续动作：`apps/server/src/openapi.ts` 需维护手写 spec 片段并与自动生成结果合并；CI 校验「接口数 = 文档路径数」（`A1` §8）。
- 排期：P2 起落地 `/api/upload/*`、`/api/raw/*`。
