# ADR-0005：输出 OpenAPI 3.1 而非引入 AI 能力

|        |                                               |
| ------ | --------------------------------------------- |
| ID     | `D5`                                          |
| 类型   | 决策（**只增不改**）                          |
| 状态   | 已接受                                        |
| 更新   | 2026-10-15                                    |
| 何时读 | 想加"AI 接口"，或改接口文档 / spec 生成方式时 |
| 规模   | ~0.5k token                                   |

## 背景

原始需求中出现「openai」，经与需求方确认，实为 **OpenAPI** 之误（原设计文档的历史结论）。需明确系统是否引入 AI 能力，以及接口如何对外暴露。

## 备选方案

| 方案      | 说明                                                                                  | 优点                                                    | 缺点                           |
| --------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------ |
| A（选中） | 不引入任何 AI 能力；把全部接口以 **OpenAPI 3.1** 规范化输出 + `/api-reference` 文档站 | 与需求本意一致；可用 openapi-generator 生成任意语言 SDK | 需维护双协议与手写 spec 片段   |
| B         | 按字面理解引入 AI 能力（如智能检索）                                                  | 字面满足需求                                            | 与需求本意不符，徒增不可控依赖 |
| C         | 忽略该需求                                                                            | 最省事                                                  | 接口无对外契约文档，集成困难   |

## 决定

**采用 A：系统不引入任何 AI 能力；所有 oRPC 过程附加 `.route()` 同时具备 RPC 与 REST 语义，输出 OpenAPI 3.1 spec（`/openapi.json`，Redis 缓存 5 分钟）与 `/api-reference`（Scalar 主题）。**

**最关键的理由：需求中的「openai」是 OpenAPI 之误，本意是要一份接口文档，不是要 AI 功能。**

刻意收窄：**不引入**任何 AI / LLM 依赖；`ai_asset` 表已从数据模型中移除（`A2` §1 注）。

## 影响

- 正面：外部系统与文档走 REST 路径 + `/api-reference`；前端仍走 `/rpc` 类型安全。
- 代价 / 后续动作：二进制路由需手写 spec 片段（`D3` → `A3` §11）；生产可用 `API_REFERENCE_ENABLED=false` 关闭文档站。
- 排期：P1 起（spec 生成与 `/api-reference`），P4 补全覆盖面。
