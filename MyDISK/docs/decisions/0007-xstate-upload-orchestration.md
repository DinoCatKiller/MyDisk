## 背景

`A6` §2.2–2.3 的上传面要求「多文件并发池 + 每文件独立暂停 / 停止 / 续传 / 重试 + 刷新恢复」。这不是一条串行流程：并发分片、失败退避、暂停须停在分片边界、刷新后对账服务端 `upload_session`（`A3` §6 / §7）。

此前的做法是隐式标志位（`isUploading` / `isPaused` / `isResuming`）驱动 UI，组合爆炸且非法状态（"暂停中又在上传"）靠约定维系，代码难以通读——这正是本决策要解决的问题：**把隐式状态换成显式状态图，且让可读性收益不只停留在转移层，而是覆盖并发编排层。**

前置约束：`D2` 定稿前端为 SolidJS **2**（当前 `solid-js@2.0.0-rc.7`）；`A3` §15 已记录一处 Solid 生态 RC 风险（`@orpc/tanstack-query`）。引入任何替代方案需先写 ADR（`AGENTS.md` §4.1）。

## 备选方案

| 方案          | 说明                                                                                                            | 优点                                                                                                                               | 缺点                                                                                                                                                                       |
| ------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A（选中）** | **`xstate` v5 核心**（框架无关）+ 机器挂**模块级 actor 池** + 自持薄订阅层（约 50 行，`createSignal` 订阅快照） | 依赖与框架解耦；并发/重试/暂停收进 `invoke` + parallel states 一个模型；状态图可由代码生成、文档不漂移；订阅层只有几十行，风险自持 | 需掌握 xstate v5 语义（actor / invoke / parallel）；订阅层要自己写一遍                                                                                                     |
| B             | 官方绑定 `@xstate/solid`                                                                                        | 现成 hooks，少写胶水                                                                                                               | peer 声明 `solid-js ^1.6.0`（`@xstate/store-solid` 为 `^1.7.0`），本项目在 `2.0.0-rc.7` **不在范围内**；绑定把 Solid 2 兼容风险引进来，且 hooks 要求机器活在组件生命周期内 |
| C             | 自研转移表 reducer（不引依赖）                                                                                  | 零依赖；转移层一眼可读                                                                                                             | 并发层要另写一套调度器，与状态机互相同步——**恰恰是最难读的部分**，本决策要解决的就是它                                                                                     |
| D（现状）     | 隐式 boolean 标志位                                                                                             | 当下零成本                                                                                                                         | 组合爆炸、非法状态靠约定；不可读                                                                                                                                           |

## 决定

**采用 A：引入 `xstate` v5 核心作为上传编排引擎，机器挂在模块级 actor 池上，组件只通过自持的薄订阅层消费快照。**

**最关键的理由：可读性与正确性的收益来自 xstate 的"状态图 + 并发编排"本身，而不是来自框架绑定——绑定只是胶水。因此把依赖收缩到框架无关的 `xstate` 核心，就把 Solid 2 的不确定性从"架构级"降为"约 50 行订阅 shim 级"。**

具体承诺：

- 引入依赖 **`xstate`**（v5，**无**框架 peer），**不承诺** `@xstate/solid` / `@xstate/store-solid`。
- 上传池**必须模块级**（不随组件 / 路由销毁），组件挂载只是订阅快照；这样刷新 / 路由切换都不中断上传。
- 每文件一台状态机，池级编排器负责并发额度与排队。

刻意收窄：

- **不**用状态机管理 UI 组件内部状态（按钮展开、表单校验仍用 signal）。
- **不**用 pnpm peer 覆盖 / `--force` 强行压掉告警安装。
- 绑定库是否最终采用，**由 spike 结果决定**，不写进本 ADR 的承诺范围。

## 影响

- 正面：上传池与组件树解耦，路由切换 / 刷新不中断；并发、退避重试、暂停语义集中在一个模型里；状态图可从代码生成，`X1` 里的图不会漂移。
- 代价 / 后续动作：新增依赖 `xstate`（即本 ADR）；需掌握 v5 的 actor / invoke / parallel 语义；自持约 50 行订阅层。
- 排期：P2（前端上传面）。`AGENTS.md` §2 地图登记 `D7`。

## 未决项

- `@xstate/solid` 在 `solid-js@2.0.0-rc.7` + 本项目实际渲染模式下能否工作 → spike 验证，结论记入 `X1`；通过则采用绑定，不通过则用本 ADR 承诺的订阅 shim 兜底。
- 刷新后恢复续传现场的持久化载体（File System Access handle / IndexedDB blob / 仅元数据靠重选） → `X1`。
